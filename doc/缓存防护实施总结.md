# Austin 缓存穿透/雪崩/击穿防护实施总结

## 📋 实施概览

本次实施完成了 Austin 消息推送平台的缓存防护机制，通过三层防护体系（缓存穿透、缓存雪崩、缓存击穿）全面提升系统的稳定性和性能。

**实施时间**: 2025-10-22  
**实施状态**: ✅ 已完成  
**影响范围**: 缓存层、数据访问层、定时任务层

---

## 🎯 核心成果

### 1. 新增核心组件（6个）

| 组件名称 | 位置 | 功能描述 |
|---------|------|---------|
| `CacheNullValueHolder` | austin-common/domain | 空值缓存对象，防止缓存穿透 |
| `BloomFilterManager` | austin-support/utils | 布隆过滤器管理器，快速判断数据存在性 |
| `DistributedLockUtil` | austin-support/utils | 分布式锁工具，防止缓存击穿 |
| `LocalCacheManager` | austin-support/utils | Caffeine 本地缓存管理器，多级缓存 |
| `CacheWarmupService` | austin-cron/service | 缓存预热服务，启动时加载热点数据 |
| `CacheMonitor` | austin-support/utils | 缓存监控组件，定时上报缓存指标 |

### 2. 改造现有模块（4个）

| 模块 | 改造内容 | 收益 |
|-----|---------|------|
| `RedisUtils` | 新增随机过期时间方法、get/delete/hasKey方法 | 防止缓存雪崩 |
| `AccountUtils` | 引入本地缓存+Redis二级缓存+随机过期 | 提升查询性能，降低Redis压力 |
| `AccessTokenUtils` | 分布式锁+空值缓存+随机过期 | 防止token刷新时的并发击穿 |
| `DataServiceImpl` | 布隆过滤器+分布式锁+缓存优化 | 防止模板查询穿透 |

## 🛡️ 三层防护体系

### 第一层：缓存穿透防护

#### 1.1 布隆过滤器
- **实现**: 基于 Redis Bitmap 实现分布式布隆过滤器
- **应用场景**:
  - API Key 查询
  - 消息模板查询
  - 渠道账号查询
- **配置**:
  - 使用 3 个哈希函数
  - 100 万个位（约 122KB 内存）
  - 误判率 < 1%

#### 1.2 空值缓存
- **实现**: `CacheNullValueHolder` 对象标记不存在的数据
- **过期时间**: 5 分钟
- **应用**: AccessToken 查询、模板查询等

---

### 第二层：缓存雪崩防护

#### 2.1 随机过期时间
```java
// 实际过期时间 = 基准时间 + [0, 20%] 随机偏移
redisUtils.setWithRandomExpire(key, value, 3600L);
```

**各场景配置**:
| 数据类型 | 基准时间 | 实际范围 |
|---------|---------|---------|
| API Key | 60 分钟 | 60-72 分钟 |
| 渠道账号 | 30 分钟 | 30-36 分钟 |
| Access Token | 根据渠道 | 动态调整 |
| 消息模板 | 15 分钟 | 15-18 分钟 |

#### 2.2 多级缓存
```
请求 → 本地缓存 → Redis 缓存 → 数据库
```

**本地缓存配置**:
- 框架: Caffeine
- 容量: 10,000 条
- 过期: 写入后 5 分钟
- 策略: LRU 淘汰

---

### 第三层：缓存击穿防护

#### 3.1 分布式锁
```java
// 使用示例
distributedLockUtil.executeWithLock("key", () -> {
    // 查询数据库并更新缓存
    return queryAndCache();
});
```

**锁参数**:
- 锁过期时间: 10 秒
- 获取锁超时: 3 秒
- 重试间隔: 50 毫秒
- 最大重试: 3 次

#### 3.2 缓存预热
**启动预热**:
- 系统启动后延迟 5 秒执行
- 加载所有消息模板 ID 到布隆过滤器
- 预热最近更新的 100 个模板到 Redis
- 加载所有渠道账号到布隆过滤器和缓存

**定时刷新**:
- 可通过定时任务定期刷新布隆过滤器
- 建议每小时刷新一次

## 🚀 性能提升预期

### 查询性能优化

| 场景 | 优化前 | 优化后 | 提升 |
|-----|-------|-------|------|
| API Key 查询 | 直接查 DB | 本地缓存 | 90%+ |
| 渠道账号查询 | 直接查 DB | 二级缓存 | 85%+ |
| 消息模板查询 | Redis + DB | 布隆 + 锁 + 缓存 | 70%+ |
| Access Token | Redis + 并发查询 | 锁 + 空值缓存 | 80%+ |

### 数据库压力降低

- **预期**: 数据库 QPS 降低 70% 以上
- **原因**: 
  - 布隆过滤器拦截无效查询
  - 多级缓存减少穿透
  - 分布式锁避免并发击穿

## 🔧 使用示例

### 1. 查询账号（多级缓存）

```java
@Autowired
private AccountUtils accountUtils;

// 自动使用本地缓存 → Redis 缓存 → 数据库
WxMpService service = accountUtils.getAccountById(accountId, WxMpService.class);
```

### 2. 获取 Access Token（分布式锁）

```java
@Autowired
private AccessTokenUtils accessTokenUtils;

// 自动使用分布式锁防止并发查询
String token = accessTokenUtils.getAccessToken(sendChannel, accountId, account, false);
```

### 3. 查询模板（布隆过滤器）

```java
@Autowired
private DataService dataService;

// 自动使用布隆过滤器 + 分布式锁 + 缓存
EchartsVo vo = dataService.getTraceMessageTemplateInfo(businessId);
```

### 4. 手动预热缓存

```java
@Autowired
private CacheWarmupService cacheWarmupService;

// 手动触发预热
cacheWarmupService.warmupAllCache();

// 增量添加到布隆过滤器
cacheWarmupService.addTemplateToBloomFilter(templateId);
```

### 5. 获取缓存监控数据

```java
@Autowired
private CacheMonitor cacheMonitor;

// 获取指定缓存的指标
CacheMonitor.CacheMetrics metrics = cacheMonitor.getMetrics("account");
System.out.println("Hit Rate: " + metrics.getHitRate());

// 检查缓存健康状态
boolean isHealthy = cacheMonitor.checkHealth();
```

## ⚠️ 注意事项

### 1. 部署建议

1. **Redis 容量规划**:
   - 布隆过滤器约占 122KB/个
   - 预计需要额外 1-2GB Redis 内存用于缓存

2. **JVM 内存调整**:
   - 本地缓存默认最大 10,000 条
   - 建议增加堆内存 512MB-1GB

3. **分布式环境**:
   - 确保 Redis 可用性（主从/集群）
   - 布隆过滤器基于 Redis，需要高可用支持

### 2. 运维建议

1. **监控告警**:
   - 接入 Prometheus + Grafana
   - 关注缓存命中率和 Redis 状态

2. **定期维护**:
   - 每周检查布隆过滤器准确性
   - 每月评估缓存容量是否需要调整

3. **降级方案**:
   - Redis 不可用时自动降级到直接查询数据库
   - 布隆过滤器失效时跳过检查（保守策略）

### 3. 开发建议

1. **新增数据**:
   - 添加模板/账号后，调用 `CacheWarmupService` 增量添加到布隆过滤器

2. **删除数据**:
   - 删除后记得清理相关缓存
   - 建议缓存空值标记防止穿透

3. **缓存失效**:
   - 修改数据后使用延迟双删策略
   - 或直接调用 `RedisUtils.delete()` 清理缓存
